# WI pagination

Source: `wi/REPORT.md` §Feed Discovery + §Request Contract (Endpoint 3) + §Enumeration, `wi/scripts/04_postback_page.py`, `07_paging_depth.py`, `08_page_blocks_and_detail.py`, `09_page_breakpoint.py`, `10_chained_paging.py`, `wi/samples/t1_page2_*`, `t1_page11_*`, `t1_chain_from11_p12_*`, `t1_break_p*`, `t1_page{20,24,25,26}_*`, `t1_paging_report_*`, `t1_blocks_*`, `t1_breakpoint_*`.

- **Mechanism:** WebForms postback, not a query param. POST to the same URL (query string included) with `__EVENTTARGET=ctl00$ContentPlaceHolder_MainBase$GridViewJobs` and `__EVENTARGUMENT=Page$<N>`, carrying the *current* page's harvested `__VIEWSTATE`/`__EVENTVALIDATION` forward. No `page=`/`start=` param exists anywhere in markup or URLs.
- **Chained state proven:** `scripts/10_chained_paging.py` harvested page 11's viewstate from the saved capture and POSTed `Page$12` with a **fresh cookie-less client** → 200, 84,480 B, `Page 12` marker, 20 new rows (`004063xxx`), no `System Error` (`samples/t1_chain_from11_p12_20261026T191513Z.html`). Each hop must use the *new* `__VIEWSTATE` from the immediately preceding response.
- **Page size:** fixed **20** — no page-size control exists on the results page (the only dropdown there is "Listed Within").
- **Hard cap: 500 rows / 25 pages per query.** The pager renders numeric links plus a `[ ... ]` block-jump link (`Page$11` from page 1, `Page$21` from page 11); pages are 1-based. The visible count is a floor (`500+ Jobs Found`), never a total.
- **Only advertised pages accepted:** `Page$13/15/17/20/24/25/26` (none present in the current pager) all returned **HTTP 200 + 39,459 B "System Error" page** (`We could not complete your request`) — always content-check, never trust status. Follow the pager's own links (including `[ ... ]`) rather than incrementing blindly.
- **Ordering:** approximately internal job-order-number descending (page 1 `00407xxxx` → page 11 `004065xxx` → page 12 `004063xxx`), **not** the visible `Date Posted`. Repeated GETs within one session are byte-identical (8/8 burst), but one of ~12 identical GETs across clients returned different page-1 rows and `(622+ openings)` vs `(525+ openings)` — consistent with two backend pools behind the F5.
- **Stop rule:** (a) no `Page$` link greater than current in `tr.pad`; or (b) fewer than 20 data rows; or (c) `System Error` body (terminal for that query — log it). Never treat an empty grid as "no jobs" without checking for `System Error`.
- **Cap handling:** `TooManyResults` non-empty (or `500+` label) → truncated at 500 → re-run sub-partitioned. Partition axes in order: `onet` (23 SOC majors) × `wd` (2/3/7/15/30) → 115 queries worst case; then geographic tiling (`loctyp`/`loc`/`dist` — `[uncertain: dist/loc semantics unprobed]`). Per-axis proof: `onet=45` → 101 jobs, `loctyp=Home` → 25 jobs, `Appr=True` → 266 jobs; `wd=2/7/30`, `onet=29/53`, unfiltered all `500+`. Whether the cross-product drives *every* partition under 500 is `[uncertain: not proven]`; SOC overlap means partitions double-count (dedupe mandatory).
- **Resume:** persist last `__VIEWSTATE` + page number per partition, or restart the partition from page 1 (≈ page-index request count — cheap either way).
- **Incremental:** `wd` takes only fixed windows, so daily delta = `wd=2` per-SOC (still `500+` unfiltered); or re-crawl page 1..k per partition and stop at the first already-seen `job_key` — but the 622-vs-525 anomaly means "top of page 1" is not a guaranteed cursor.
- **Cost:** ~1 GET + (pages−1) POSTs per partition (26 requests for a saturated 500-row partition, 1–6 for a small one); full sweep ≈ **150–400 requests** at 1.5–2 s spacing, sequential per partition, parallel across partitions.
