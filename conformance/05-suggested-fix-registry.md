# Suggested-fix registry — conformance suite

## 1. Scope and acceptance boundary

This suite targets `contracts/05-suggested-fix-registry.yaml`, contract version `suggested-fix-registry/0.1.0`, including its local definitions, ownership rules, reference ordering, and all `FIX-*` semantic rules. Structural validation alone is insufficient. [extracted: contracts/05-suggested-fix-registry.yaml]

The suite verifies that a recorded finding can support a scoped, reviewed, falsifiable recommendation without becoming an implemented repair, a successful application, or permission to act. It also verifies that withholding a recommendation remains a useful, valid outcome. [inferred: 1-handoff-brief.txt, Parts VII–IX]

Step 0 delivers this specification and the schema, not an operating registry. The tests below use deterministic synthetic evidence, an in-memory journal/artifact store, and authority stubs; they require neither a rule-matching service nor a live browser. Registry implementation remains deferred to Hellscape M3. [proposed: enforce the schema now without moving the deferred registry implementation into the critical path]

A component must pass its applicable consumer or producer tests against these doubles before peer integration. Circus Tent and Ringmaster run independently; neither product's passing result qualifies the other. [inferred: 1-handoff-brief.txt, silo-test discipline and independent execution products]

A real manual application, an empty registry, and an M1 diagnostic with a reasoned null recommendation remain valid. This suite must not become a prerequisite for applying to a job manually or for Hellscape M1 acceptance. [extracted: contracts/05-suggested-fix-registry.yaml, x-contract.implementation]

**Execution status:** specification only; no test execution or repaired product is claimed by this document. [proposed: distinguish the conformance deliverable from an execution receipt]

## 2. Runner and result discipline

### 2.1 Proposed deterministic entry point

The following is an implementation target, not a claim that the runner or fixture directory already exists: [proposed: provide an unambiguous future verification command]

    python tools/conformance/check_suggested_fix_registry.py \
      --schema contracts/05-suggested-fix-registry.yaml \
      --fixtures testdata/conformance/suggested-fix-registry \
      --offline

The runner must resolve schema references locally, disable network access, fix fixture inputs and ordering, and hash actual generated bytes. It must not download artifacts, invoke a subject, perform employer writes, execute rule text, or modify product source. [proposed: keep schema conformance deterministic and separate from executing a verification plan]

The runner's output must identify the schema digest, fixture-catalog digest, validator identity, expanded case inventory, per-case assertions, observed results, and retained evidence references. Any reported elapsed measurements use the evidence kernel rather than ad hoc timestamps. [proposed: make a conformance result reproducible and independently inspectable]

Use these process dispositions; they describe the test run, not a native subject or application outcome. [proposed: adapt the retired qualification harness's exit discipline]

| Exit | Meaning | Epistemic status |
|---|---|---|
| `0` | Every required assertion completed with its expected result. | [proposed: deterministic suite success] |
| `1` | At least one completed assertion disagreed with its oracle. | [proposed: measured conformance failure] |
| `2` | Required tooling, configuration, or fixtures were unavailable before the relevant tests could run. | [proposed: distinguish blocked setup from product failure] |
| `3` | Runner, fixture, hashing, or evidence integrity failed. | [proposed: distinguish harness failure from a valid negative test] |
| `4` | The required case inventory was not fully executed or retained. | [proposed: skipped required tests cannot pass] |
| `130` | Operator interruption. | [extracted: 5-browser-qualification.md, exit codes] |

A deliberate corrupt-artifact test passes when the implementation detects the corruption; it does not make the runner itself an integrity failure. An unavailable artifact needed to establish the test oracle, by contrast, prevents the test from passing. [proposed: separate injected failures from broken test infrastructure]

### 2.2 Three assertion surfaces

Tests distinguish record acceptance, recommendation eligibility, and verification interpretation. These labels are suite notation, not additions to the registry wire schema. [proposed: prevent valid-but-ineligible proposals from being rejected as malformed records]

| Surface | Oracle notation | Meaning | Epistemic status |
|---|---|---|---|
| Record validation | `ACCEPT` | Structural, reference, authority, and applicable semantic checks pass. | [proposed: complete validation oracle] |
| Record validation | `REJECT(layer)` | Reject at `schema`, `reference`, `authority`, or `semantic`; retain a useful diagnostic. | [proposed: localize contract failures] |
| Recommendation | `EMIT` | Emit the exact eligible `FixReference`, not a patch or success claim. | [extracted: contracts/05-suggested-fix-registry.yaml, FIX-RECOMMEND] |
| Recommendation | `WITHHOLD` | Emit `Missing` with an allowed reason and useful detail; preserve the proposal for inspection when valid. | [extracted: contracts/05-suggested-fix-registry.yaml, Recommendation and FIX-RECOMMEND] |
| Verification | Exact per-check result | Preserve `comparison_validity`, `oracle_result`, evidence, and limitations for each planned check. | [extracted: contracts/05-suggested-fix-registry.yaml, VerificationCheckResult] |

An accepted unreviewed class is not an approved class. An accepted suspected instance is not an eligible recommendation. An eligible recommendation need not have been implemented or verified. A `criterion_met` result means only that the named plan predicate was met in its tested scope. [extracted: contracts/05-suggested-fix-registry.yaml, FIX-CLASS-REVIEW, FIX-ATTRIBUTION, FIX-RECOMMEND, and FIX-VERIFY]

### 2.3 Validation layers

Run the following layers separately so a permissive schema validator cannot hide a missing semantic check. [proposed: make the contract's non-JSON-Schema obligations executable]

1. **Decode and schema:** reject duplicate YAML keys and non-JSON values; enforce JSON Schema 2020-12, closed objects, constants, enums, and local references. [extracted: contracts/05-suggested-fix-registry.yaml, x-validation]
2. **Reference resolution:** resolve exact bytes, digests, journal events, pointers, prefixes, diagnostic findings, class reviews, plans, and snapshot selections. [extracted: contracts/05-suggested-fix-registry.yaml, x-validation]
3. **Authority:** establish writers and human reviewers from trusted ingestion evidence, never from caller-supplied identity strings alone. [extracted: contracts/05-suggested-fix-registry.yaml, x-ownership and x-validation]
4. **Semantics:** apply all relevant `FIX-*` rules, including complete evidence/check matrices, scope, attribution, chronology, revocation, and verification interpretation. [extracted: contracts/05-suggested-fix-registry.yaml, x-semantic-rules]
5. **Effects:** assert that validation, matching, approval, publication, and receipt interpretation cause no product patch, browser operation, new commission, or active-task change. [extracted: contracts/05-suggested-fix-registry.yaml, FIX-NO-AUTO-PATCH]

## 3. Fixture construction

### 3.1 Shared fixture mechanics

Fixture builders must emit complete records accepted by the schema; the descriptions below are construction instructions, not abbreviated payloads permitted on the wire. Every required field is populated, and unavailable values use `Missing`. [proposed: keep readable test specifications without weakening complete-record validation]

Generate digests with the contract's `kernel-jcs-sha256/1` convention for canonical JSON records and hash exact stored bytes for other artifacts. Generate real journal chains and resolvable pointers; do not use placeholder hashes in accepted fixtures. [extracted: contracts/05-suggested-fix-registry.yaml, x-compatibility.canonicalization and FIX-JOURNAL]

The authority stub supplies authenticated principals and role grants out of band from submitted records. It includes a curator, publisher, human reviewer, consumer assessor, verifier, target-product owner, and an unprivileged model principal. The same human may hold several roles; the role exercised for each write remains explicit. [proposed: test writer separation without requiring multiple people or deployed services]

Use synthetic candidate data and a synthetic secret canary only. All evidence units are labeled according to their actual synthetic origin; fictitious product version keys must never be presented as installed releases or current production observations. [proposed: exercise privacy and scope without importing personal data or manufacturing operational evidence]

For each negative case, change one semantic condition at a time. Unless testing hash or chronology corruption, rebuild dependent artifacts and registration events in that case's independent fixture so all unrelated references remain valid. Never alter a previously accepted record in the same fixture history to make an illegal mutation appear legitimate. [proposed: isolate the intended failure while preserving immutability tests]

[proposed: make plans resolvable and bounded without invoking native execution]

### 3.3 Registration order

Use this order, with each object's evidence prefix stopping before its own registration: source observations → `D0` registration → class registration → human review registration → plan registration → instance registration → snapshot publication → `D1` publication → new candidate observations → receipt registration. The plan refers to the future instance by stable ID, not its future digest. [extracted: contracts/05-suggested-fix-registry.yaml, x-reference-order and FIX-JOURNAL]
