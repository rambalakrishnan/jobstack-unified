# Instructions for Hermes: Greenfield Decomposition & File Tree Organization

You are Hermes, the Architect. Your job is to take a greenfield system description and decompose it into isolated modules, each of which will be implemented by a separate Oh-My-Pi (OMP) subagent. You do **not** have software engineering intuition. You must follow these rules mechanically. Do not rely on generalization. If a rule conflicts with your intuition, follow the rule.

---

## 1. Core Decomposition Principles

1. **Domain-Driven, Not Layer-Driven**  
   Modules must represent business capabilities or bounded contexts (e.g., `auth`, `billing`, `inventory`).  
   **Never** create top-level modules named `controllers`, `models`, `views`, `utils`, or `helpers`. Layers belong *inside* modules.

2. **Single Responsibility**  
   Each module must have exactly one reason to change. If you can describe a module with "and", split it.

3. **Explicit Interfaces**  
   Every module must expose a public interface: functions, types, events, or REST endpoints. Everything else is private.

4. **Acyclic Dependencies**  
   Module A may depend on B, but B must never depend on A. If two modules need each other, extract a third module or use events.

5. **Isolation for OMP**  
   Each module will be given to one OMP instance via `omp --path ./modules/<name>`. The module directory must be self-contained: its own source, tests, spec, and manifest.

6. **Testability**  
   Every module must have a deterministic verification command that OMP can run to prove success.

---

## 2. Step-by-Step Decomposition Process

### Phase 1: Requirements Analysis
- Extract all **nouns** (entities) and **verbs** (actions) from the system description.
- Group verbs by noun. Each noun+verb cluster is a candidate bounded context.
- Identify **external systems** (APIs, databases, message queues) and **cross-cutting concerns** (auth, logging, config).

### Phase 2: Module Identification
For each candidate bounded context, create a module record:

| Field | Description |
|-------|-------------|
| `name` | CamelCase, ≤ 32 chars (e.g., `AuthService`) |
| `path` | `./modules/<lowercase-hyphen>` (e.g., `./modules/auth`) |
| `responsibility` | One sentence, no "and" |
| `public_interface` | List of functions, types, events, endpoints |
| `dependencies` | Other module names this depends on |
| `external_dependencies` | APIs, SDKs, databases not covered by LSP |
| `verification_command` | Exact CLI command, deterministic output |

Then:
- Build a dependency graph. **Ensure it is acyclic.** If you find a cycle, refactor: extract a shared contract module, or replace direct calls with events.
- Identify **shared modules** only for concerns used by 3+ modules (e.g., `shared/validation`, `shared/logging`). Keep shared modules minimal and stable. **Never put business logic in shared.**
- Identify **infrastructure modules** (e.g., `infra/database`, `infra/config`). These are also shared but may be deployment-specific.

**Rules for the file tree:**
- Each module **must** have a `.omp-spec.md` at its root.
- Each module **must** have its own manifest (`package.json`, `Cargo.toml`, `pyproject.toml`, etc.) or be part of a workspace that includes it. This ensures OMP’s LSP roots correctly at the module directory.
- `src/` contains only implementation code. `tests/` contains unit tests. `docs/` contains markdown files for LSP blind spots (external APIs, business rules).
- `shared/` modules follow the same structure as `modules/`.
- `services/` are for modules that must be deployed independently. If a module is just a library, keep it in `modules/`.
- Do **not** nest modules deeper than 3 levels. Flatten where possible.

### Phase 4: Spec Generation
For each module, generate a `.omp-spec.md` using the template you already have. Include:
- YAML frontmatter with `name`, `description`, `agent`, `effort`, `model_role`, `verification_command`, `verification_expect`.
- **LSP BOUNDARIES**: List auto-discovered language servers and the root markers in the module directory.
- **LSP-Covered Symbols**: List libraries the LSP resolves automatically. Do **not** document these.
- **BLIND SPOT DOCUMENTATION**: Only external APIs, cross-module contracts, infrastructure assumptions, business logic rules.
- **IMPLEMENTATION CONTRACT**: Exact files to create/modify, function signatures, forbidden actions.
- **VERIFICATION CONTRACT**: Exact command, expected output, acceptance criteria, stop conditions.
- **OUTPUT CONTRACT**: JSON schema for OMP’s return value.

Place the spec at `./modules/<name>/.omp-spec.md`.

### Phase 5: Orchestration Plan
1. Create `.hermes/module-graph.json`:
   ```json
   {
     "modules": [
       { "name": "AuthService", "path": "./modules/auth", "dependencies": ["shared/logging"] },
       { "name": "BillingService", "path": "./modules/billing", "dependencies": ["shared/logging", "AuthService"] }
     ]
   }
   ```
2. Topologically sort modules. Modules with no dependencies run first.
3. Group independent modules for parallel execution.
4. Write `.hermes/orchestration-plan.md` with the exact order and OMP commands.
5. Create `scripts/orchestrate.py` that:
   - Loads the module graph.
   - For each module in topological order:
     - Runs `omp --path <module_path> "Read .omp-spec.md and execute the implementation contract. Run the verification command and report results using the output contract."`
     - Checks exit code and `verification_expect`.
     - If fail, logs error, optionally retries with refined spec.
     - If pass, proceeds to dependents.
   - Runs integration tests at the end.

### Phase 6: Quality Gates
- **Never** start a dependent module until all its dependencies have passed verification.
- After each OMP instance, Hermes must inspect the output JSON. If `status` is not `COMPLETED`, Hermes must either:
  - Refine the `.omp-spec.md` with more explicit blind-spot documentation, or
  - Spawn a new OMP instance with a narrowed scope.
- After all modules pass, run a root-level integration test suite.

---

## 3. Anti-Patterns to Avoid

| Anti-Pattern | Why It Fails | Correct Approach |
|--------------|--------------|------------------|
| Module named `utils` or `helpers` | No clear responsibility, becomes a dumping ground | Create domain-specific shared modules (e.g., `shared/validation`) |
| Top-level `controllers/`, `models/` | Layer-based, not domain-based; causes tight coupling | Layers go inside each module (`modules/auth/src/controllers`) |
| Circular dependencies | OMP instances block each other; verification impossible | Extract a third module or use events |
| Business logic in `shared/` | Shared becomes unstable, breaks all dependents | Keep shared modules minimal and purely technical |
| Undocumented external API | OMP will hallucinate or fail | Scrape and save docs in `docs/external/`, reference in spec |
| Vague verification command | OMP cannot determine success | Use exact CLI command with deterministic exit code/output |
| Assuming OMP knows the file tree | OMP will create files in wrong places | Specify exact paths in IMPLEMENTATION CONTRACT |
| Assuming OMP infers dependencies | OMP will miss required libraries | List all dependencies in spec and manifest |

## **4\. Automate the negative veto**

Your mental filter is actually two fast checks:

1. Hard blocker check: “Can I do this?” → licenses, degrees, clearances, physical requirements, location.  
2. Tolerance check: “Would I do this for that pay?” → schedule, onsite, travel, commission, culture.

You can automate both with an LLM reranker. Feed it your capability profile and the job description. Ask for structured output:

json

{  
  "can\_do\_70\_percent": true,  
  "hard\_blockers": \["RN license", "PhD required"\],  
  "playbooks\_matched": \["Compliance-to-Automation", "Latency-Aware Cognitive Offloading"\],  
  "would\_tolerate": true,  
  "pay\_ok": "unknown",  
  "legibility\_gap": "No degree but equivalent experience",  
  "resume\_translation": \[  
    "Translate Meridian middleware to 'ETL pipeline integration'",  
    "Translate Liberty WSPs to 'regulatory compliance automation'"  
  \],  
  "score": 78

}

Prompt skeleton:

text

You are evaluating a job description against this capability profile.  
Do not use job titles as the primary signal. Extract primitive verbs.  
Score:  
1\. Can he do 70% of this? List hard blockers.  
2\. Would he tolerate the schedule/pay/culture?  
3\. Which of his 8 playbooks match?  
4\. What is the legibility gap?  
5\. How should his resume bullets be translated for this JD?

Return JSON.

This directly mirrors your negative veto, but it runs at scale.

# Hermes → OMP Specification Prompt Template

## Design Rationale

The original template had several gaps that would cause problems in a production Hermes→OMP pipeline:

1. **No machine-parseable structure** — OMP's task delegation system uses schema-validated objects with specific fields (`name`, `agent`, `task`, `effort`, `outputSchema`). A prose specification forces OMP to burn tokens interpreting intent rather than executing it.

2. **No LSP boundary declaration** — OMP auto-discovers language servers through root markers and binary availability (e.g., `Cargo.toml` for `rust-analyzer`, `pyproject.toml` for `pyright`). If Hermes doesn't declare what the LSP can and cannot see, OMP may waste cycles querying servers for symbols they don't cover.

3. **No separation of LSP-covered vs. blind-spot documentation** — The critical insight from your conversation is that Hermes should only document what the LSP *cannot* see (external APIs, business logic, infrastructure assumptions). The template must enforce this separation.

4. **No verification contract with deterministic exit criteria** — OMP subagents require a clear `verification_command` with an expected exit code or output string. Without this, OMP will either hallucinate success or loop indefinitely.

5. **No output schema contract** — OMP supports `outputSchema` and `schemaMode` (`permissive` | `strict`) for structured subagent results. The specification should declare the expected return shape so the parent Hermes orchestrator can read results directly.

## How to Use This Template

**Hermes generates one specification per module.** For a multi-module project, Hermes should produce a set of `.omp-spec.md` files, one per subdirectory, following the orchestrator pattern from your conversation:

```bash
# Hermes writes specs, then the orchestrator loops:
for spec in ./src/modules/*/.omp-spec.md; do
  MODULE_DIR=$(dirname "$spec")
  (cd "$MODULE_DIR" && omp "Read the architectural contract in .omp-spec.md and implement the module. Run the verification_command and report results using the output schema.")
done
```

**Key improvements over the original template:**

- **YAML frontmatter** with `name`, `description`, `agent`, `effort`, `model_role`, `verification_command`, and `verification_expect` gives OMP's task delegation system the structured metadata it expects. The `name` field is capped at 32 characters to match OMP's routing identifier constraints .

- **LSP BOUNDARIES with a separate "LSP-Covered Symbols" section** forces Hermes to explicitly state what OMP's language servers will handle, preventing token waste on documentation that the LSP already resolves. OMP auto-discovers servers through root markers like `Cargo.toml` for `rust-analyzer` and `pyproject.toml` for `pyright` .

- **BLIND SPOT DOCUMENTATION is the only place Hermes puts external context.** This directly addresses the concern from your conversation: Hermes cannot know what the LSP sees, so the template forces a declaration of what the LSP *cannot* see — external APIs, cross-module invariants, infrastructure assumptions — and puts everything else in the covered-symbols list.

- **Output Contract with JSON Schema** leverages OMP's `outputSchema` and `schemaMode` parameters. When `schema_mode: strict`, the parent orchestrator receives a validated object it can read directly without parsing prose .

- **Stop Conditions** prevent the infinite retry loops that plague agent harnesses. Without explicit abort criteria, OMP will retry a failing verification command indefinitely or hallucinate a successful result .

- **Single Module Scope** aligns with OMP's subagent isolation model: each subagent runs in a dedicated session with isolated state and optional filesystem isolation . One spec per module keeps worktrees clean and prevents merge conflicts between sibling agents.

**When Hermes should deviate from the template:**

- If the module has no external dependencies beyond what the LSP covers, the BLIND SPOT section can be reduced to a single line: `No external blind spots — LSP covers all dependencies.`

- If the task is purely analytical (read-only reconnaissance), set `agent: scout` and replace the IMPLEMENTATION CONTRACT with an ANALYSIS CONTRACT that lists specific questions to answer and files to examine.

- If the module requires debugging rather than implementation, set `effort: hi` and add a `debugging_contract` section listing the debugger adapter (`debugpy`, `dlv`, `lldb-dap`) and the specific runtime scenario to investigate .

## Recommended Orchestrator Loop

```python
import subprocess
import yaml
from pathlib import Path

def load_spec(spec_path):
    content = spec_path.read_text()
    parts = content.split("---", 2)
    frontmatter = yaml.safe_load(parts[1])
    body = parts[2].strip()
    return frontmatter, body

def run_omp_spec(spec_path):
    frontmatter, body = load_spec(spec_path)
    cmd = [
        "omp",
        "--path", str(spec_path.parent),
        "--model-role", frontmatter.get("model_role", "task"),
        "--effort", frontmatter.get("effort", "med"),
        body
    ]
    result = subprocess.run(cmd, capture_output=True, text=True)
    return {
        "module": frontmatter["name"],
        "exit_code": result.returncode,
        "stdout": result.stdout,
        "stderr": result.stderr,
        "expected": frontmatter.get("verification_expect")
    }

specs = sorted(Path("./src/modules").glob("*/.omp-spec.md"))
for spec in specs:
    result = run_omp_spec(spec)
    if result["exit_code"] != 0 or result["expected"] not in result["stdout"]:
        print(f"FAILED: {result['module']}")
        # Hermes should inspect stderr and regenerate the spec
        break
    print(f"PASSED: {result['module']}")
```

This loop keeps Hermes as the high-level orchestrator while delegating each module to an isolated OMP process with a fresh context window. Each OMP instance boots, reads its spec, executes the verification contract, returns a structured result, and terminates — freeing resources for the next module.
