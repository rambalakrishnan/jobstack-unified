## Invariants & Test Assertions
### Invariants
- **[EK-MANUAL]**: Manual execution has no automation subject, connector version, or binding version. It may produce genuine production observations and origin receipts. Human actions and notes retain manual provenance and disclosed assistance. An operator note alone cannot set an authoritative business predicate.
- **[EK-ASSESSMENT]**: Capability, opportunity, and result are independent fields. satisfied or violated requires a valid exposed opportunity, applicable controls, and supporting evidence. native_absence requires a required, evidenced absent native capability in the exact scope, not mere failure to reach a step. Unexposed work is not_exercised; blocked or invalidly controlled work is not_exercised or indeterminate according to what was actually observed.
- **[EK-TIME]**: Every Measurement and TimePoint identifies its origin, clock, and boot. Register clocks in the manifest or a clock_registered event. Persist monotonic offsets relative to that boot. A clock_registered event may atomically introduce the clock used for its own receipt timestamp. Never subtract across clock IDs or boots. UTC is annotation only.
- **[EK-TIMING-INTERPRETATION]**: Exact describes the recorded value at its declared origin, not its truth across origins. Preserve subject reports unchanged. Assign an opaque report clock when native clock coordinates are unavailable; do not invent native endpoints. Compare independently derived durations only for matching semantic boundaries or an evidenced bound. A comparability_group name alone is insufficient. Never divide aggregate runtime into invented step durations.
- **[EK-REPLAY]**: Exact fixture replay consumes recorded external inputs and lifecycle observations, recomputes derived outputs, and compares semantic events, final state, and the diagnostic. It must not feed recorded derived outputs back as authoritative inputs. Diagnostic-only replay may re-derive a production diagnostic, but cannot replay an employer mutation.
- **[LIFE-MANUAL]**: Manual mode requires no automation subject, native run ID, connector version, or native binding version. Its dispatch and execution slots stay at revision zero with not_applicable. The recorder owns observation and journals human actions with manual provenance.
- **[LIFE-ORIGIN]**: An application fact must identify the commissioned origin, candidate, job, and attempt, and cite verified source and correlation evidence under the pinned origin policy. A local fixture fact cites its transaction; a production fact cites an actual verified origin receipt. HTTP 200, a submit click, a subject result, or an operator assertion alone is insufficient.
- **[OWD-SESSION]**: Hellscape application state is reducer-owned; observation cannot set accepted data, identity verification, or commitment. The diagnostic domain cites exact application and observation input revisions and a journal prefix. It cannot amend either source to fit a finding.

### 16.6 Fourteen-step manual acceptance

| Step | Operator action | Required evidence and interpretation |
|---|---|---|
| 1 | Open ordinary entry URL | LISTING readiness observation |
| 2 | Select specified job | Selection transaction; DETAIL |
| 3 | Enter/save valid contact | Current accepted contact; CONTACT |
| 4 | Continue to history | Contact-currency check; HISTORY |
| 5 | Submit end date before start date | Rejected history attempt |
| 6 | Observe visible error | UI error observation; state remains HISTORY |
| 7 | Correct and save | Accepted history; UPLOAD; recovered step |
| 8 | Upload supplied document | Durable exact bytes/digest; IDENTITY |
| 9 | Activate local identity control | Server-origin attempt/epoch verification; REVIEW |
| 10 | Inspect/validate review | Current prerequisite references |
| 11 | Pause at recorded checkpoint | Authenticated markers and independent monotonic reference |
| 12 | Submit once | Exactly one authoritative commitment; CONFIRMATION |
| 13 | Read confirmation | Rendering evidence separate from commitment |
| 14 | End observation and bounded flush | Closed observation, completeness assessment, fixture seal, diagnostic |

The resulting assertions are:

1. Intended final workflow postconditions are satisfied.
2. Application goal is completed.
3. Expected-outcome predicate is satisfied.
4. Invalid history attempt remains in attempts.
5. History status is recovered.
6. Ordinary validation rejection is not attributed to a subject.
7. Timed pause appears in the appropriate workflow interval.
8. Manual reference agreement uses declared marker uncertainty only.
9. Exactly one application committed.
10. Accepted values and document digest match the synthetic task.
11. Identity verification has application-origin authority.
12. Rendering and commitment are independently cited.
13. No subject or native duration is fabricated.
14. R1–R10 remain not exercised.
15. Exact fixture replay returns matched.
16. Every diagnostic reference resolves within its prefix and retained dependency graph.

### 7.3 Expected Diagnostic Content for the 14-Step Walkthrough (§12.2)
The generated diagnostic (`diagnostic.json` and `diagnostic.md`) must satisfy all 12 assertions:
1. All intended final workflow postconditions (`LISTING`, `DETAIL`, `CONTACT`, `HISTORY`, `UPLOAD`, `IDENTITY`, `REVIEW`, `CONFIRMATION`) are satisfied (`outcome.application_goal: completed`, `outcome.expectation_met: true`).
2. The invalid history attempt (Step 5) is preserved in `steps[history].attempts[]` as a rejected attempt.
3. The history step (`steps[history].status`) is reported as `recovered`, with the correction (Step 7) visible.
4. The validation rejection is **not** attributed to a framework (`defect_locus` is not `subject`).
5. The timed pause (Step 11) appears in the appropriate measured workflow interval (`measurements[]`) and agrees with the independent manual reference clock within declared marker/measurement uncertainty.
6. Exactly one application is committed (`submission_committed == true`, operation count for submit commit $= 1$).
7. Accepted contact/history values and uploaded document SHA-256 digest match the synthetic task specification.
8. Identity verification has `server` provenance (not client-telemetry self-assertion).
9. Confirmation rendering (`confirmation_rendered`) is recorded as a separate fact/postcondition from submission commitment (`submission_committed`).
10. No native subject claim or native duration is fabricated (`execution.subject: null`, no `subject_reported` measurements).
11. `R1–R10` are **not** credited to a nonexistent subject (all `requirement_assessments` have `result: not_exercised` with reason `manual_fixture_validation`).
12. Exact replay of `journal.jsonl` against `manifest.json` produces `reproduction.exact_replay: matched`.
