### 18.1 SLM transformation

Input is `{target,job_id,title,employer,snippet_or_description,source_url,posted_date}`.

Canonicalization applies NFC, newline normalization, outer trimming, optional-empty substitution, ISO date formatting, then the five-field newline payload:

`title`, `employer`, `snippet_or_description`, `source_url`, `posted_date`.

The hash includes canonical text, stage, and model version. Stage/model are separate execution metadata but still explicit hash inputs. Cookies, authorization, profile fingerprint, worker, lease, and batch identity are excluded.

Outputs must match target, job, stage, model, and input hash; genuine/applied verdicts use PASS/VETO; confidence is finite `[0,1]`; reason is bounded and nonempty. Duplicate/malformed/mismatched outputs are inference errors, never implicit PASS.

Batch limits: at most 25 items, at most 20 ms collection dwell, manifest token budget, default 2,000 ms inference timeout. Long input is not silently truncated. Deterministic complete-input decomposition requires a manifest contract.

Before dispatch:

\[

Partial item success is allowed. Late responses after release, expiry, revision change, or model mismatch are fenced.

Timeout/failure increments retry once and releases ownership. With bypass disabled, preserve pending or terminate exhausted retries. With bypass enabled, complete the stage with null genuine verdict, applied PASS, explicit bypass reason, and no classifier row.

Snippet shadow is initially on for MN/MI and off for other surfaces. Dynamic mode pins an externally supplied revision at claim. Missing/conflicting updates retain the last valid revision, otherwise safe shadow on. In-flight policy does not change. Description classification is never shadowed by snippet mode.

### 21.3 Resource and performance contract

Crawler defaults remain deployment declarations:

- Cold worker target 200 MB.
- Warm worker target `(N+1)×130+70` MB.
- Orchestrator target 200 MB.
- Aggregate embedded storage target 100 MB.
- SLM nominal 600 MB–2.5 GB; class targets 1 GB/3 GB.
- Default declared overshoot maximum 25%, with justification.
- SLM batch target 100–200 ms under the reference ≤512-token envelope; not a supplied benchmark.
- Navigation ceilings remain target-wide.
- Default response bound 64 MiB and streaming buffer 1 MiB.
- Queue default 10,000 rows plus explicit byte bound.
- Microbatching at most 1 ms.

Inference runs in a separately bounded process/domain with host admission reserving crawler/storage/OS resources. An SLM-induced crawler OOM invalidates the run, stops claims, and prevents successful completion representation. It is not an ordinary retry.

Pagination orchestration median must be ≤10% of measured network median. Network, bootstrap, downstream inference, explicit admission wait, and synchronous signal blocking are separately measured, not hidden.

Signals contain stage rows in/out, stage latency, queue depth, request overhead, and sink latency. Sink calls hold no session, transaction, completion, or V8 lock. Median sink latency above 100 ms over five minutes marks degraded throughput; a stuck sink cannot recursively emit its own latency.

### 4.B Session Sharding Topologies, `!Send` Thread Confinement & Rotating Cookie Serialization

#### 1. Four Session Sharding Topologies (§9.1–§9.4)

1. **`none` (`MN-A`, `MN-B`, `IL-A`, `IL-B`, `WI-A`):**
   - `shard_id = null`.
   - **Zero `session_state` rows are written.**
   - In-process HTTP cookie jar and connection pool may still exist (does not create a new TCP socket per request).
2. **`per_crawl_run` (`MI-A`):**
   - `shard_id = 'shared'`.
   - Shared state resides in the live `HttpClient` session (`HttpClient::shared(profile)` or retained client passed through `navigate_with_init(client)`, never an independent-pool `HttpClient::clone()`).
   - Cannot be combined with a `challenge_clear` bootstrap (§4.2 validation constraint).
   - Session-stateful request steps are strictly serialized (`max_inflight_per_session = 1`) even when multiple workers exist.
3. **`per_worker` (`WI-B`, `MI-B`):**
   - `shard_id = 'worker_<N>'`.
   - Dedicated session generation per worker (`WI-B` via external headed sidecar Handoff; `MI-B` via cold `Page` clearance-cookie harvest + HTTP verification).
   - `max_inflight_per_session = 1`.
4. **`per_shard` (`OR-A`, `OR-B`):**
   - `shard_id = 'shard_<I>'` with initial deployment declaration `shard_count = 2` per slot.
   - `OR-A` and `OR-B` maintain completely independent live rotating session generations and never share or replay a frozen cookie snapshot.
   - Because `browser_oxide`'s `SharedSession` is process-wide, independent rotating shards use separate engine processes (`engine_session_domain`) unless explicit engine-level namespacing is verified (Decision 2).

#### 2. `!Send` Thread Confinement Contract (§5.5, §9.3)

- `browser_oxide::Page` is strictly `!Send` and bound to its allocating OS thread for its entire lifetime (creation, navigation, `Page::from_html`, solver execution, `reset_for_reuse`, and destruction).
- No `Page`, solver instance, DOM reference, V8 isolate handle, or closure capturing one may ever cross an OS-thread boundary.
- Cross-thread messages may contain only owned bytes, immutable request/profile descriptions, IDs, session epochs, and permitted `Send` `HttpClient` handles.

#### 3. Rotating-Session & Cookie Serialization Protocol (§3.6, §9.4)

For `Stateful-rotating` slots (`OR-A`, `OR-B`, rotating cookie `OClmoOot`):

1. **Single In-Flight Request Gate:** `max_inflight_per_session = 1`; at most one request affecting a rotating cookie jar is in flight at any instant (preventing RFC 6265 concurrent `Set-Cookie` race conditions).
2. **Synchronous Sequential Cookie Application:** Every response's `Set-Cookie` mutations are applied to the live `HttpClient` cookie jar **before** the next request is prepared.
3. **Complete Hop Coverage:** Redirect responses and solver-generated requests are included in the serialized sequence.
4. **Monotonic Sequencing:** Both `request_sequence` and `cookie_generation` increase strictly monotonically; cookie snapshot publication to `session_state` occurs after cookie application and `last_committed_request_sequence` advancement.
5. **Single-Owner Epoch Fencing:** A session generation `(target, run_id, phase, shard_id, session_epoch)` has at most one active `owner_epoch`; stale owners attempting publication have their response and cursor commit rejected.
6. **Non-Replayable Snapshots:** Persisted encrypted `cookie_jar_snapshot` blobs in `session_state` are recovery/diagnostic evidence, never static tokens redistributed across threads or replayed after an unacknowledged crash.
7. **Cold Crash Recovery:** After an owner crash, a rotating session is always re-established via a fresh cold `Page` bootstrap rather than trusting an unacknowledged snapshot.

### 4.C Credit-Before-Wire Joint Deadlock Protocol (Decision 2)

Resolves the joint deadlock between downstream bounded-queue back-pressure (`queue_max_capacity = 10,000`, `queue_max_bytes`) and proactive/reactive session replacement (`replacement_deadline = session_expires_at - session_rebootstrap_buffer`):

1. **Credit-Before-Wire Admission:** Before issuing any wire request, the worker reserves sufficient durable capacity in the downstream queue and `staging_disk_budget_bytes` for the maximum admitted response packet (`max_rows_per_response`, `max_response_bytes`) and all generated entity references.
2. **Guaranteed Post-Wire Materialization:** No admitted wire response ever waits for new downstream queue capacity to commit its durable entity transaction, apply rotating cookies, and advance `cursor_state`.
3. **Producer Pause at Capacity:** When row or byte admission reaches capacity, new data request admission pauses; already-reserved in-flight requests drain and commit cleanly.
4. **Reserved Independent Control Lane:** Each active target reserves at least `control_reserve_slots >= 1` with independent command capacity, CPU admission, and cold-bootstrap memory admission outside the data queue.
5. **Lease-Free Bootstrap:** Cold `Page` bootstrap and session replacement never claim or wait on a `listing`, `work_item`, or `job_detail` lease.
6. **Unblocked Deadline Replacement:** When `now >= replacement_deadline` (or reactive lapse occurs), session replacement executes immediately through the reserved control lane even if all data queues are 100% full.
7. **Orderly Old-Owner Drain & Fence:** The retiring owner drains its single in-flight request (`max_inflight_per_session = 1`), applies the response's rotating cookie update, commits its cursor boundary, and is fenced by incrementing `owner_epoch` / `session_epoch`.
8. **`Send` Live-Client Handoff:** The replacement bootstrap verifies the session over HTTP and publishes the `Send` live `HttpClient` handle plus new `session_epoch`. No `!Send` `Page` or solver crosses threads.
9. **Deliberate Quiescence on Prolonged Saturation:** If queue saturation persists beyond `queue_saturation_grace_ms` (default `5,000 ms`), the shard transitions to `session_state.status = 'quiescent'` and retires the session rather than endlessly re-bootstrapping an idle blocked pipeline.
10. **Low-Water Mark Resumption:** Data admission resumes only after queue occupancy drops below `queue_resume_low_watermark` (default `0.8` of both `queue_max_capacity` rows and `queue_max_bytes`), establishing a fresh cold session generation if the shard had become `quiescent`.
