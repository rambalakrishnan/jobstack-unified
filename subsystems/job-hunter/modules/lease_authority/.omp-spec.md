## Invariants & Test Assertions
### Invariants
- **[EK-LEASE]**: Claim atomically checks eligible resource state and absence of an unexpired lease, assigns a unique fencing lease_id and owner epoch, advances the entity revision, clears last_failure_reason, and appends evidence without changing resource_state. Completion checks lease ID, unexpired authority-clock deadline, entity/input revisions, and applicable owner/session epochs. A rejected stale completion has no effect.
- **[EK-LEASE-RESTART]**: leased_at and lease_expires_at use one registered lease-authority clock and boot; expiry must be later than issue. Renewal requires a still-current token and epoch. On authority restart, durably fence the old authority epoch before reclaiming its leases. Never compare old offsets with the new boot, and never infer elapsed downtime from UTC.
- **[EK-TIME]**: Every Measurement and TimePoint identifies its origin, clock, and boot. Register clocks in the manifest or a clock_registered event. Persist monotonic offsets relative to that boot. A clock_registered event may atomically introduce the clock used for its own receipt timestamp. Never subtract across clock IDs or boots. UTC is annotation only.
- **[EK-ATOMICITY]**: A locally authoritative operation commits its admitted input, idempotency record, authoritative effects, journal events, and replayable response as one owner-local durable effect before acknowledgement. Install referenced artifact bytes durably before that commit. Cross-owner publication remains asynchronous; this rule does not authorize a shared transaction across owners.
- **[LIFE-IDEMPOTENCY]**: The commissioning idempotency key is scoped to the commissioning principal and immutable attempt request. Same key and request returns the same local attempt/handle; changed content under the key is rejected. Repeated Start does not launch a second logical execution.
- **[OWD-REVISION]**: A domain revision is a complete immutable snapshot, not a patch. revision=previous_revision+1 at the owner. The first revision is 1. The key (entity, domain, revision) identifies exactly one content digest. Identical retries are idempotent; different bytes under that key are an integrity conflict. Stale expected revisions or lease epochs cannot commit.

### 15.5 Product leases

Product work uses kernel leases independently of crawler leases.

The lease record retains resource, policy, issuer, authority epoch, entity/input revisions, generation, resource and eligible state, lease state, token, owner, owner/session epochs, issue/expiry points, retries, failure reason, prefix, and evidence.

Claiming does not change resource state. Completion checks current token, unexpired authority-clock deadline, revisions, and epochs. Stale completion has no effect. Failed generations increment retries at most once.

Authority restart durably fences the old epoch. Lease expiry revokes local commit authority, not evidence that native work or employer transactions stopped.

### 13.2 Failure recovery

| Failure | Required action |
|---|---|
| Prepare response lost | Retry identical command; no hidden replanning |
| Stale preparation | Reject; no silent reprepare |
| Start response lost | Retry same command/key |
| Delivery may have occurred | Preserve uncertainty; observe and reconcile |
| Native acceptance known, terminal response lost | Continue observation; do not relaunch |
| Late callback | Authenticate, correlate, append |
| Transport closed | Do not infer cancellation |
| Lease expired | Fence local commit only; do not infer noncommitment |
| Executor unavailable after uncertain delivery | No automatic executor switch |
| Artifact lost | Preserve known identity and record loss |
| Journal repair needed | Never repeat employer mutation to repair local evidence |

Resume requires existing handle/key, same request/context, checkpoint artifact, native resume contract, authorization, evidence, and an open observation window. `ResumeAuthorization` contains `handle`, `checkpoint`, `native_resume_contract`, `authorization_refs`, and `evidence_refs`.

Resume uses a new command identity but the same logical execution. It never repeats completed side-effecting steps.
