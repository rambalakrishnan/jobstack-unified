## Invariants & Test Assertions
### Invariants
- **[EK-ATOMICITY]**: A locally authoritative operation commits its admitted input, idempotency record, authoritative effects, journal events, and replayable response as one owner-local durable effect before acknowledgement. Install referenced artifact bytes durably before that commit. Cross-owner publication remains asynchronous; this rule does not authorize a shared transaction across owners.
- **[LIFE-DISPATCH]**: Prepare is non-executing. Before the first native delivery, durably allocate the connector-local handle and record the intended request digest, idempotency key, and dispatching transition. A native run ID is attached only when actually received and correlated. Local Start acknowledgement is not native acceptance; native acceptance is not execution completion.
- **[LIFE-IDEMPOTENCY]**: The commissioning idempotency key is scoped to the commissioning principal and immutable attempt request. Same key and request returns the same local attempt/handle; changed content under the key is rejected. Repeated Start does not launch a second logical execution.
- **[EXT-START]**: Before wire delivery, durably commit the local handle, immutable request binding, idempotency association, and dispatch intent under owner-local fencing. Start returns a local receipt without awaiting task completion. A native run ID is attached only in later source-backed observations.
- **[EXT-IDEMPOTENCY]**: For mutating/collecting calls, (authenticated principal, connector_id, request_id) identifies one command. Same command and identical request returns its retained receipt without another effect; conflicting content under that key is rejected. Describe and Observe are read calls whose responses may reflect newer evidence.
- **[EXT-RESUME]**: Resume requires a new command identity, the existing logical idempotency key/handle, explicit recovery authority, and an evidenced native checkpoint or idempotency contract for the same request and context. It preserves the same logical dispatch and journals each additional delivery.
- **[EXT-BOUNDS]**: Enforce finite local call, queue/observation, drain, cancellation-wait, and cleanup-wait bounds using registered local monotonic clocks. Admission and observation buffering are bounded; rejected work is not silently lost. An accepted queued task consumes its active observation budget.
- **[OWD-LOCAL-COMMIT]**: Commit an owner's authorized effect, revision advance, and journal evidence atomically within that owner's durability boundary. Do not acknowledge before durability. No owner commit acquires a peer-owned write lock or waits for a peer transaction, acknowledgement, or large-payload serialization.

### 4.3 Local scheduling states

These are proposed local states, not shared lifecycle enums.

| State | Entry | Allowed continuation |
|---|---|---|
| `admitted_queued` | Durable handle and logical binding | Assigned, expired-before-entry, fenced |
| `assigned` | Current resource/worker ownership | Entry-pending, expired-before-entry, fenced |
| `entry_pending` | Intent and arguments durable | Entered, expired-before-entry, fenced |
| `entered` | Native entry observed | Returned, failed, unresolved |
| `returned` | Return evidence retained | Next authorized step or finalization |
| `failed` | Definite failure retained | Explicit safe recovery or finalization |
| `unresolved` | Completion/effect not established | Late evidence, reconciliation, authorized containment |
| `expired_before_entry` | Boundary reached before entry | No workflow delivery |
| `fenced` | Ownership or command authority revoked | No workflow delivery |

A blocked noninterruptible call does not block local finalization. The owner may remain unresolved. It is not silently replaced by another execution.

### 13.4 StartRequest and durable admission

StartRequest contains `preparation`, `idempotency_key`, `accepted_concern_ids`, `authorization_refs`, and `recovery`.

Before delivery, owner-locally commit the local handle, immutable request association, logical idempotency binding, command deduplication, dispatch intent, and replayable response.

ConnectorHandle contains:

- `record_type: connector_handle`
- `schema_version`
- `handle: {connector_id, local_handle}`
- `preparation`
- `scope`
- `idempotency_key`
- `created_at`

StartResult contains `kind: start_receipt`, `disposition: accepted_locally | existing_handle | resume_authorized`, `handle`, `handle_artifact`, and `receipt_ref`.

The same command returns its retained receipt. Repeated initial Start under the same logical key returns the same handle. An application commission cannot obtain a second logical execution by changing keys, callers, or executors.

### 16.3 DispatchValue

Required fields:

`state`, `local_handle`, `native_run_id`, `request_digest`, `delivery_refs`, `acceptance_refs`, `recovery_authorization_refs`, `reason`.

| From | Allowed next states |
|---|---|
| Unpublished | not_started, prepared, rejected |
| not_started | prepared, rejected |
| prepared | dispatching, rejected |
| dispatching | accepted, rejected, uncertain |
| uncertain | uncertain, accepted, rejected |
| accepted | accepted |
| rejected | rejected |

Dispatching requires durable handle/request/intent before delivery. Accepted requires correlated native evidence, not Start acknowledgement. Rejected after possible delivery requires nonacceptance evidence. Lost response is uncertain.

Same-state revisions add evidence but never authorize a second execution. Authorized resume preserves logical accepted state and records additional delivery.

## 18. Lease, recovery, and crash semantics

When Ringmaster uses leased resources, it consumes the exact kernel LeaseRecord, not a worker-authored claim token.

| Lease fields | Mapping |
|---|---|
| `record_type`, `schema_version` | Exact lease record |
| `resource` | owner_domain, entity_type, entity_id of the actual resource |
| `policy` | Owner-specific eligibility/TTL/retry/routing pin |
| `issuer_id`, `authority_epoch` | Actual lease authority and lifetime |
| `entity_revision`, `input_revision`, `generation_id` | Fenced resource/input generation |
| `resource_state`, `eligible_state` | Owner state; claim does not change it |
| `lease_state` | unleased or held |
| `lease_id`, `lease_owner`, `owner_epoch`, `session_epoch` | Current fencing identities |
| `leased_at`, `lease_expires_at` | One registered authority clock/boot |
| `retry_count`, `max_retries_effective`, `last_failure_reason` | Owner retry policy state |
| `journal_prefix`, `evidence_refs` | Supporting durable evidence |

Unleased ownership/time fields are inapplicable. Held records require lease identity, owner, epoch, issue/expiry, compatible state, and applicable session epoch.

Claim atomically checks eligibility and absence of an unexpired lease, advances revision, clears failure reason, and appends evidence. Completion checks lease, expiry, revisions, and epochs. Stale completion has no effect.

Release, expiry, and confirmed-death recovery clear ownership atomically. A failed generation increments retries at most once. Successful completion is not a failed retry.

Authority restart fences its old epoch before reclamation; old/new monotonic offsets are never compared. Reclamation revokes local commit authority, not proof that a worker or employer transaction stopped.

| Crash boundary | Required recovery |
|---|---|
| Before durable Start | No acceptance claim |
| After local admission, before delivery | Recover same handle; deliver only within remaining authority |
| Around native delivery | Preserve uncertainty unless stronger evidence exists |
| After side effect, before local result | Never replay merely to repair journal |
| During artifact install | Do not publish absent bytes |
| After artifact install, before registration | Recover/register under owner policy; no external rerun |
| After registration, before response | Same command returns retained receipt |
| During native owner loss | Fence dependent commands; retain unresolved effects |
| After observation closure | Append late evidence; never reopen window |
