## Invariants & Test Assertions
### Invariants
- **[LIFE-COMMISSION]**: Commission before an authorized automated dispatch. Freeze attempt identity, kind, candidate, job snapshot, target, task, execution configuration, owner bindings, and permissions. The commission must agree with the admitted manifest and be journaled before Start can cause a native request. Changing the subject version, target, kind, or task creates a new attempt.
- **[EXT-TASK]**: Match the full task, scope, permissions, observation policy, assistance, and selected subject to the admitted manifest. Application work additionally matches its immutable commission, including kind and lineage. Manual commissions are not dispatchable through this contract.
- **[EXT-PREPARE]**: Prepare is non-executing. Validate already supplied task data, plan, dependencies, mappings, grants, and declared limits without visiting the target, testing authentication, resetting context, invoking a planner, or secretly improving the plan. Record the native serialization and subject-facing task independently.
- **[EXT-PREPARATION-PIN]**: A preparation is immutable and names the exact descriptor, subject, mapping, full task, delivered task, intended native request, runtime-access references, and limitations. Start accepts that preparation digest, including all concerns requiring acceptance, under actual task authority.
- **[EXT-IDEMPOTENCY]**: For mutating/collecting calls, (authenticated principal, connector_id, request_id) identifies one command. Same command and identical request returns its retained receipt without another effect; conflicting content under that key is rejected. Describe and Observe are read calls whose responses may reflect newer evidence.
- **[EXT-STATE-POLICY]**: Browser-state and framework-learning-state requests remain separate. Prepare records their mapping and limitations; actual realization is journaled after Start. An opaque context reference is not a Page or DOM handle and grants no authority by itself.
- **[EXT-DECLARE-NOT-ASSESS]**: The connector declares capabilities, mappings, observations, and source claims. It does not emit qualification, requirement satisfaction, or an authoritative application-success flag. Consumer assessment remains separate from capability availability and opportunity.

### 13.3 PreparedTask

Required fields:

| Field | Source |
|---|---|
| `record_type`, `schema_version`, `preparation_id` | Immutable preparation identity |
| `scope`, `configuration`, `task` | Exact validated inputs |
| `task_semantic_hash` | Contract 02 semantic canonicalization |
| `assistance`, `planning_evidence_refs`, `runtime_access` | Validated declared assistance/access |
| `delivered_task`, `delivered_task_hash` | Exact subject-facing bytes and digest |
| `native_request`, `native_request_hash` | Exact intended native request and digest |
| `translation` | Pinned translator |
| `budget_mapping` | Exactly five dimensions |
| `concerns` | All nonblocking limitations |
| `evidence_prefix` | Supporting input/decision prefix |

Semantic hashing removes task_id and replaces entry URL and origin strings with their logical IDs, preserving all other values and array order. Equal semantic hash does not authorize changed actual destinations.

Native request bytes exclude runtime credentials/signatures as specified by Contract 02. Planning measurements remain supporting evidence, not undeclared PreparedTask fields.

BudgetMapping contains `dimension`, `enforcer: connector | subject | not_enforced | not_applicable`, `evidence_refs`, and `limitations`.

PreparationConcern contains `concern_id`, `category`, `disposition`, `detail`, and `evidence_refs`. Categories are native_capability_absent, native_capability_unknown, budget_not_enforced, state_policy_unverified, assistance_limit, observation_limit. Disposition is requires_acceptance or informational.

PrepareResult contains `kind: prepared`, `preparation`, and `record`. PreparationReference contains `preparation_id`, `artifact`, and `registration_ref`.
