## Invariants & Test Assertions
### Invariants
- **[EK-CAPABILITY]**: A descriptor applies to exactly one subject_id, subject_version, configured mode, and interface surface. Its catalog must enumerate every capability for that scope. Every new subject version starts unknown until its own evidence establishes another availability. Omission and predecessor descriptors do not imply inheritance, presence, or absence.
- **[EXT-DESCRIBE]**: Pin a descriptor to one subject/version/configured mode/interface surface. A new subject version starts unknown on every capability until its own evidence establishes another availability. Neither presence nor absence inherits. Documentation can support a declaration, not a run-success result.
- **[EXT-DECLARE-NOT-ASSESS]**: The connector declares capabilities, mappings, observations, and source claims. It does not emit qualification, requirement satisfaction, or an authoritative application-success flag. Consumer assessment remains separate from capability availability and opportunity.
- **[BO-CAPS]**: Capability evidence is scoped to the exact binding build, engine build, configuration, mode, and interface surface. A new subject version starts unknown. Mapped does not mean exercised; unsupported mapping does not establish native absence. Capability, opportunity, and result remain separate in the consumer's diagnostic.

### 12.3 CapabilityDescriptor

Required fields are `record_type`, kernel `schema_version`, `descriptor_id`, `descriptor_revision`, `declared_by`, `subject`, `catalog`, `evidence_prefix`, `supersedes`, and `capabilities`.

Each CapabilityRecord contains `capability_id`, `requirement_refs`, `availability`, `claim_origin`, `evidence`, and `limitations`.

Availability is present, absent, unknown, or not_applicable. Claim origin is native, composed_subject, or harness. Evidence items contain `basis: documentation | executed_observation | source_diagnosis | operator_attestation` and `ref`.

Non-unknown availability requires evidence. No predecessor or binding descriptor automatically establishes product availability.

Minimum external catalog:

`native_goal_task`, `native_plan_execution`, `native_cancel`, `native_context_release`, `native_artifact_retrieval`, `native_revision`, `native_dom_access`, `browser_state_isolation`, `browser_state_persistence`, `learning_state_control`.

### 12.4 Operation and task mappings

OperationMapping contains `operation`, `implementation: connector_local | native_mapping | unmapped`, `native_contract`, `capability_refs`, `evidence_refs`, and `limitations`.

| Verb | Ringmaster mapping |
|---|---|
| Describe | Local descriptor read |
| Prepare | Local validation/serialization |
| Start | Local durable admission plus established native task-delivery mapping |
| Observe | Local journal projection |
| RequestNativeCancel | Established native task-cancel mapping or explicit unmapped handler |
| CloseObservationConnection | Local transport/window handling |
| CollectArtifacts | Local retained artifacts; native retrieval only if evidenced |
| ReleaseNativeContext | Exact evidenced context release or unmapped |
| Contain | Authorized installed harness policy |

TaskMapping contains `task_type`, `input_form: goal | recorded_plan | extraction_request | crawl_declaration`, `mapping`, `planning_owner`, `recovery_owner`, and `limitations`.

Only one mapping per task type is advertised. Configured mode selects goal versus recorded-plan apply; incomplete translation fails.
